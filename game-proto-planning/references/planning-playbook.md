## GDD 缺口檢查問題庫

用途:讀完使用者草稿後,對照這裡找出沒想清楚的地方。**不要整份丟給使用者**——挑出他文件裡真的缺或矛盾的,才拿出來問。原型階段優先問標【原型關鍵】的項目。

### 0. 核心驗證目標【原型關鍵】
最重要,通常也最常缺。
- 這個原型做出來,你想證明或回答什麼問題?(例:「這種操作手感好不好玩」「這個關卡機制做不做得出來」)
- 怎樣算驗證成功?怎樣算失敗?
- 如果只能做出一件事,那件事是什麼?

### 1. 核心玩法循環 (Core Loop)【原型關鍵】
- 玩家在最小一段遊玩裡,反覆做的動作是什麼?(30 秒~2 分鐘的循環)
- 這個循環的節奏:行動 → 結果 → 回饋 → 下一步,每一環是什麼?
- 為什麼這個循環會讓人想再玩一次?

### 2. 玩家操作與輸入【原型關鍵,動作設計專長區】
- 玩家用什麼輸入?(鍵鼠/手把/觸控)按鍵配置?
- 每個核心動作對應什麼輸入、什麼回饋(動畫/音效/畫面)?
- 手感相關:有無加速度、緩衝、輸入預留(input buffer)、取消(cancel)等需求?
- 這些是不是原型要驗證的重點?若是,要在 GDD 寫清楚預期手感。

### 3. 目標感受與體驗
- 想讓玩家玩的時候有什麼感覺?(緊張/爽快/解謎的滿足/放鬆)
- 參考作品是什麼?哪裡想學、哪裡想不一樣?

### 4. 勝負 / 結束條件
- 一場遊玩怎麼結束?(通關/死亡/時間到/分數)
- 有沒有失敗?失敗的後果?
- 有沒有進程或成長?(原型常可先砍掉,問清楚是否需要)

### 5. 系統與機制
- 除了核心循環,還有哪些機制?每個機制服務於什麼?
- 哪些機制是原型必要、哪些可以之後再加?
- 機制之間有沒有互相依賴或衝突?

### 6. 內容範圍
- 原型需要幾個關卡/場景/角色/敵人?最小是多少?
- 美術風格方向?(原型可用暫代素材 placeholder 嗎?)

### 7. 技術與風險
- 有沒有你沒做過、不確定做不做得出來的部分?(這是最該先驗證的)
- 用什麼引擎/工具?

### 缺口分析輸出方式
把找到的缺口分組,每組幾個問題,附上「為什麼要問」。範例:

> **核心驗證目標**(這段你的文件還沒寫,但它會決定其他所有取捨)
> 1. 這個原型最想證明的一件事是什麼?
> 2. 怎樣算成功?
>
> **操作手感**(你提到是動作遊戲,但沒寫輸入方式)
> 3. 用手把還是鍵鼠?
> 4. 跳躍/攻擊各對應什麼鍵,預期什麼手感?

## WBS 分類與估算

原型由個人獨立製作,**不做人力分配**。WBS = 工作項目清單,每項含:項目、交付物、依賴、粗估規模。

### 分類(依交付物性質分,不是依人分)

1. **程式 / 系統**——核心玩法程式、輸入處理、狀態機、UI 邏輯、存檔等。使用者專長非程式時,這區的不確定性最高,拆細一點並標風險。
2. **遊戲動作設計**——角色動作規格、手感參數、攻擊判定/受擊、動畫狀態切換設計。使用者專長區,可拆較細以利掌控。
3. **美術 / 平面**——角色/場景/UI 圖、動畫、特效、icon。原型可先用暫代素材,標明哪些是暫代、哪些要正式。
4. **關卡 / 內容**——關卡設計、敵人配置、數值調整、測試關。
5. **整合與測試驗證**——把上面組起來、跑通、驗證核心假設。**這一區直接對應原型的存在目的,不可省**。

### 估算規模
用相對規模 S / M / L,或粗略人日。原型階段不必精確,重點是抓相對大小與依賴。
- S:半天~1 天內。
- M:2~3 天。
- L:4 天以上——**L 項目要警惕**,考慮能否再拆或縮範圍。

### 原型範圍紀律
每個項目問一句:「這個不做,核心假設還驗證得了嗎?」
- 驗證得了 → 標【原型後】或砍掉。
- 驗證不了 → 保留,且優先。

寧可清單短。個人原型最大的風險是範圍膨脹做不完。

## 時程排法

依 WBS 排時程,**用假設工作日估算,不接行事曆**。

### 步驟
1. **確認投入量**:每週幾個工作天?每天幾小時?哪天開始?未知就用預設(每週 5 天)並註明「此為假設,請修正」。
2. **規模轉人日**:S/M/L → 人日(S≈1、M≈2.5、L≈5,可依專案調)。
3. **依賴排序**:被依賴的先做(例:輸入系統 → 角色動作 → 關卡測試)。
4. **風險前置**:不確定做不做得出來的、驗證核心假設的,盡量排最前面。愈早撞到問題,愈有時間應對。這是個人原型排程的第一原則。
5. **加緩衝**:個人開發者容易低估。總工時抓 20~30% 緩衝,尤其風險項。
6. **標里程碑**:如「核心玩法可驗證」「首個可玩版本」「原型完成」。里程碑對應可檢視的成果,不是日期本身。

### 輸出重點
- 用階段/週來排,不用綁死到某月某日(除非使用者要)。
- 明列所有假設(投入天數、規模換算、緩衝比例)。
- 結尾明說「這是建議版,時程一定要依實際狀況修正」。
