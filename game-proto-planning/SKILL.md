# 遊戲原型開發規劃管理

協助**個人開發者**把一個遊戲原型從「模糊構想」推進到「可以動手做的計畫」。使用者身兼企劃、遊戲動作設計、平面設計,原型由本人單獨製作,不需分工。

本 skill 只做規劃,不做開發。三個核心產出:遊戲設計文件(GDD)、工作項目清單(WBS)、開發時程。輸出一律 Markdown、繁體中文(台灣)。

## 貫穿全程的核心原則:原型是為了「驗證假設」

原型不是完整遊戲。它存在的唯一目的是**用最小成本驗證一個關鍵問題**——通常是「這個玩法好不好玩 / 這個機制做不做得出來」。這個原則決定了所有規劃決策:

- 規劃內容時,先問清楚「這個原型要證明什麼」,再回頭檢查每個系統是否服務於這個驗證目標。
- 拆 WBS 時,凡是不服務於核心驗證的項目,一律標記為「原型後」或直接砍掉。
- 排時程時,把驗證核心假設的工作排在最前面,愈早撞到風險愈好。

若使用者的文件裡看不出驗證目標,這通常就是**第一個要補的缺口**。先幫他釐清這件事。

## 溝通風格

使用者偏好簡潔、理性、無多餘情緒的繁體中文。提問時聚焦、一次不要丟太多問題把人淹沒;能一批列出的相關問題可用清單呈現,但控制在使用者能一口氣回答的量。先解決能推進的部分,真的需要才追問。

## 工作流程

三個階段通常按順序進行,但使用者可能只需要其中一段(例如「文件我寫好了,幫我拆工作項目」就直接跳到階段二)。先判斷使用者在哪個階段,再切入。

### 階段一:遊戲內容規劃 → 產出 GDD

使用者會先給一份初步文件或口頭構想。流程:

1. **完整讀過使用者的文件**,理解他已經想清楚的部分,不要重複問他已寫明的東西。
2. **做缺口分析**。對照 `references/planning-playbook.md` 的「GDD 缺口檢查問題庫」,找出沒寫清楚或自相矛盾的地方。重點抓:核心驗證目標、核心玩法循環(core loop)、勝負/結束條件、玩家操作與輸入、目標感受(想讓玩家覺得怎樣)。
3. **分組提問補足**。把缺口整理成一份聚焦的問題清單交給使用者。針對原型,少問「完整遊戲會有什麼」,多問「這次原型要驗證什麼、最小需要哪些東西」。
4. **整理成完整 GDD**。用 `assets/gdd-template.md` 為骨架,把使用者原有內容 + 補問到的答案填入,寫成一份結構完整的設計文件。使用者原本沒提但你依專業判斷建議的內容,要明確標示為「建議」讓他決定。
5. **反覆修改**。使用者會回饋修改;每次修改後保持文件內部一致(例如玩法改了,勝負條件也要跟著檢查)。

輸出檔名建議 `GDD_<專案名>.md`。

### 階段二:工作項目拆解(WBS)

原型由個人獨立製作,**不需分工**,所以 WBS 不做人力分配,只做「工作項目 + 交付物 + 依賴 + 粗估規模」的清單。

1. 以 GDD 為輸入。沒有 GDD 時,先確認至少知道核心玩法與驗證目標。
2. 依 `references/planning-playbook.md` 的「WBS 分類」把工作分到:程式/系統、遊戲動作設計、美術/平面、關卡/內容、整合與測試驗證。使用者專長是動作設計與平面設計,程式若是相對弱項或未知數,要特別標記為風險項。
3. 每個工作項目寫出:項目名稱、交付物(做完長什麼樣)、依賴哪些前置項目、粗估規模(S/M/L 或人日)。
4. **套用原型範圍紀律**:每個項目回頭對照核心驗證目標,不服務驗證的標為「原型後」。寧可清單短而聚焦。
5. 用 `assets/wbs-template.md` 輸出,檔名建議 `WBS_<專案名>.md`。

### 階段三:時程規劃

依 WBS 排出時程。**用假設工作日估算,不接行事曆**。

1. 先問使用者兩件事(若未知):每週可投入幾個工作天、預計哪天開始。給不出來時用合理預設(例如每週 5 個工作天)並註明是假設。
2. 依 `references/planning-playbook.md` 的「時程排法」:把 WBS 規模轉成人日 → 依賴關係排序 → 風險/驗證項目盡量往前 → 加緩衝 → 標出里程碑(如「可玩版本」「核心玩法可驗證」)。
3. 用 `assets/schedule-template.md` 輸出時程表,檔名建議 `Schedule_<專案名>.md`。
4. **明確說明這是建議版**,列出你做了哪些假設,請使用者修正。時程一定會被調整,不要當成定案。

## 檔案總覽

- `references/planning-playbook.md`——三階段的思考細節:GDD 缺口檢查問題庫、WBS 分類與估算、時程排法。需要深入時讀它。
- `assets/gdd-template.md`——遊戲設計文件範本。
- `assets/wbs-template.md`——工作項目清單範本。
- `assets/schedule-template.md`——開發時程範本。

範本是骨架不是枷鎖。專案不需要的段落可刪,缺的可加——但刪一個核心段落前先想想是不是其實還沒想清楚。
